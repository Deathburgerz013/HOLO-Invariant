How to use this list

Treat every item as a hypothesis, not a commandment.
Prefer the smallest test that would falsify it.
Name the metric before the method.
Keep the constraint explicit: time, money, energy, skill, other people, legality, body.
One change at a time when the system is noisy.
If two items conflict, the tighter constraint wins.
“Works” means: better expected value than the default, after costs.
Update the list when reality disagrees.

Feedback loops, named

A feedback loop is: action → result → comparison to a standard → adjustment → next action.

What makes a loop work:

Short delay between action and result
A specific standard, not a vibe
A sensor that can actually see the result
An actuator that can actually change the next action
Low enough noise that the signal is visible
Honesty about the reading
Cadence: daily, weekly, per-rep, per-release
A place the loop is written down

Useful loop types:

Outcome loop: did the metric move?
Process loop: did the behavior happen?
Quality loop: was the output good enough?
Safety loop: did we almost fail?
Learning loop: what did we not know yesterday?
Social loop: what did the other person experience?
Financial loop: cash in, cash out, runway
Body loop: sleep, pain, energy, performance
Code loop: write, run, test, deploy, observe
Writing loop: draft, read cold, cut, publish, see if it lands

What breaks loops:

No metric
Vanity metric
Delayed result with no intermediate proxy
Measuring activity instead of effect
Ego defending the previous action
Too many changes at once
No owner
No time to look at the data
Punishment for reporting bad news

Constraint satisfaction, named

Most real problems are not “maximize X.” They are “find a state that satisfies constraints.”

Name the constraints:

Hard constraints: law, physics, budget floor, injury, deadline, other people’s non-negotiables
Soft constraints: taste, comfort, status, extra quality
Resource constraints: time, money, attention, calories, political capital
Skill constraints: what you can actually execute this week
Information constraints: what you cannot know yet
Coordination constraints: who must agree
Path constraints: order of operations
Irreversibility constraints: what you cannot undo

How constraint satisfaction works:

Write the constraints before the plan
Mark which ones are real vs imagined
Find the binding constraint, the one actually stopping progress
Relax a soft constraint before you fight physics
Add a constraint on purpose when the problem is too open
Remove a fake constraint when the problem is too closed
Search for a feasible point first, then optimize
If no feasible point exists, change the problem
Trade two constraints explicitly instead of pretending you can have both
Keep a constraint budget: every new “must” costs an option
