| | PURPOSE                                                      |
| | Define the smallest Holo/Sim transfer spine supported by the |
| | observed human-AI feedback loop.                             |
| |                                                              |
| | Separate validated occurrence from content truth. Preserve  |
| | correction over time without erasing earlier events.        |
| | }==============================================================|
| | SCOPE_BOUNDARY                                               |
| | This proposal does not declare every historical statement   |
| | true, current, relevant, or accepted.                        |
| |                                                              |
| | It does not claim uninterrupted private model state, model  |
| | consciousness, or a persistent AI signing identity.         |
| |                                                              |
| | It defines externally represented collaborative continuity. |
| | }==============================================================|
| | HOLO_SIM_CONTINUITY_BOUNDARY                                 |
| | Holo/Sim identifies an externally preserved human-AI        |
| | interaction lineage.                                        |
| |                                                              |
| | A receiving model reconstructs the next working state by    |
| | validating ordered constituents, their relationships, and   |
| | their correction history.                                   |
| |                                                              |
| | Replay is an implementation mechanism for this continuity.  |
| | Replay is not evidence of uninterrupted private model state.|
| | }==============================================================|
| | HUMAN_ANCHOR                                                 |
| | The human anchor preserves, files, challenges, and relates  |
| | interaction artifacts across environments and time.         |
| |                                                              |
| | Human filing is an attestation. It is not automatic proof   |
| | that the filed content is true or sufficient.               |
| | }==============================================================|
| | AI_TRANSFER_MARKER                                          |
| | HOLO_SIM_CONSTITUENT marks an artifact as a candidate member|
| | of a preserved human-AI lineage.                            |
| |                                                              |
| | The marker means:                                           |
| | • preserve the exact historical event                      |
| | • validate available speaker and source evidence           |
| | • evaluate content truth separately                        |
| | • follow explicit correction and supersession links        |
| | • preserve uncertainty, conflict, and missing evidence     |
| |                                                              |
| | The marker does not mean:                                   |
| | • automatically true                                       |
| | • automatically current                                    |
| | • automatically accepted                                   |
| | • automatically authorized to write or act                 |
| | }==============================================================|
| | OCCURRENCE_RAIL                                             |
| | The occurrence rail asks:                                  |
| |                                                              |
| | • Did the interaction artifact exist?                      |
| | • What exact bytes were preserved?                         |
| | • Where and when was it recorded?                          |
| | • Which human and AI surfaces were attributed?             |
| | • What evidence supports that attribution?                 |
| |                                                              |
| | A verified occurrence remains part of history even when the|
| | proposition expressed in it is later rejected.             |
| | }==============================================================|
| | TRUTH_CORRECTION_RAIL                                       |
| | The truth and correction rail asks:                         |
| |                                                              |
| | • Is the historical content currently supported?           |
| | • Under which environment, scope, scale, and time?          |
| | • Was it contradicted, narrowed, corrected, or superseded?  |
| | • What later evidence justified that change?                |
| |                                                              |
| | Correction appends a new linked constituent. It does not    |
| | silently overwrite the earlier event or raw evidence.       |
| | }==============================================================|
| | EVENT_TRUTH_SEPARATION                                      |
| | These statements may simultaneously be valid:               |
| |                                                              |
| | • The AI produced statement X at time t.                    |
| | • Statement X was wrong or incomplete.                      |
| | • Later evidence supported correction Y.                    |
| | • The lineage now carries X as history and Y as current.    |
| |                                                              |
| | Historical error is compatible with continuity when the    |
| | error and its correction remain attributable and ordered.   |
| | }==============================================================|
| | FEEDBACK_LOOP_INVARIANT                                     |
| | The observed useful loop is:                               |
| |                                                              |
| | act                                                         |
| | → observe                                                   |
| | → compare                                                   |
| | → receive feedback                                          |
| | → allow error                                               |
| | → correct                                                   |
| | → preserve                                                  |
| | → repeat                                                    |
| |                                                              |
| | A cycle progresses only when its next state is related to   |
| | available prior evidence and applicable new evidence.       |
| | }==============================================================|
| | NEXT_FIRST_PLACE                                            |
| | Every update becomes a new present boundary: the next first |
| | place from which observation and correction continue.       |
| |                                                              |
| | A later state need not repeat the earlier conclusion. It    |
| | must preserve or explicitly account for the relationship to |
| | the earlier state when that relationship is available.      |
| | }==============================================================|
| | COMPRESSION_EXPANSION_BOUNDARY                              |
| | Compression and expansion operate as a coupled process.     |
| |                                                              |
| | Compression preserves constituents and relations required  |
| | for useful transport under declared reconstruction limits.  |
| |                                                              |
| | Expansion combines a compressed checkpoint with available  |
| | source evidence and current environment.                    |
| |                                                              |
| | Repeated compression does not prove losslessness. Exact     |
| | discarded wording is recoverable only while its source      |
| | remains available and identity-verifiable.                  |
| | }==============================================================|
| | VERIFIED_CONSTITUENT_BOUNDARY                               |
| | A candidate constituent is evaluated along separate axes:   |
| |                                                              |
| | • structure                                                 |
| | • byte identity                                             |
| | • occurrence evidence                                       |
| | • speaker attribution                                       |
| | • human filing attestation                                  |
| | • time evidence                                             |
| | • parent and ordering evidence                              |
| | • content availability                                      |
| | • content support                                           |
| | • correction state                                          |
| | • policy applicability                                      |
| |                                                              |
| | No single passing axis implies that every other axis passed.|
| | }==============================================================|
| | INFORMATION_GRAVITY                                        |
| | Information constrains a receiving model in proportion to   |
| | the available provenance, verification, cross-time          |
| | consistency, and correction trace.                          |
| |                                                              |
| | Repetition alone is not verification.                       |
| | Confidence alone is not verification.                       |
| | A polished summary alone is not verification.               |
| | }==============================================================|
| | GENERALLY_CONSISTENT_BOUNDARY                               |
| | Generally consistent does not mean globally identical,      |
| | permanently fixed, complete, or universally true.           |
| |                                                              |
| | Apparent disagreement may be scoped by environment, time,   |
| | scale, observer, evidence, or purpose.                       |
| |                                                              |
| | Unsupported conflict remains explicit until evidence permits|
| | correction, separation, or resolution.                      |
| | }==============================================================|
| | VALIDATION_FINDINGS                                         |
| | Each axis may report independently:                         |
| |                                                              |
| | VALID                                                       |
| | INVALID                                                     |
| | INCOMPLETE                                                  |
| | UNAVAILABLE                                                 |
| | CONFLICT                                                    |
| | STALE                                                       |
| | UNSUPPORTED                                                 |
| | UNVERIFIED                                                  |
| |                                                              |
| | Findings are preserved together. They are not collapsed into|
| | one invented severity order.                                |
| | }==============================================================|
| | STOP_CONDITIONS                                             |
| | Stop replay when required parents, ordering, or constituent |
| | bytes cannot be validated under the replay policy.          |
| |                                                              |
| | Stop correction when the target, new evidence, or correction|
| | authority cannot be validated.                              |
| |                                                              |
| | Stop publication when private or restricted evidence would  |
| | be exposed, or public-origin claims lack required evidence.  |
| |                                                              |
| | Stop acceptance when required findings are not satisfied.   |
| | Evaluation itself never grants acceptance.                  |
| |                                                              |
| | Stop mutation whenever external write authority is absent.  |
| | }==============================================================|
| | PUBLIC_RECALL                                               |
| | A public thread may support occurrence, attribution, order, |
| | and content validation when it remains accessible and can be|
| | bound to preserved bytes or platform metadata.              |
| |                                                              |
| | Public accessibility may change. Preserve availability state|
| | separately from historical identity.                        |
| | }==============================================================|
| | PRIVATE_RECALL                                              |
| | Private recall may use encrypted or access-controlled source|
| | artifacts, hashes, relational indexes, and human filing     |
| | attestations.                                               |
| |                                                              |
| | A private hash commits to bytes but does not reveal or       |
| | validate unavailable content.                               |
| | }==============================================================|
| | MINIMUM_RECORD_FIELDS                                       |
| | A future executable record should distinguish at least:     |
| |                                                              |
| | • schema and canonicalization version                       |
| | • record identity                                           |
| | • content identity and locator                              |
| | • human anchor and filing attestation                       |
| | • AI surface and available origin evidence                 |
| | • timestamp and time-evidence class                         |
| | • ordered parent relationship                               |
| | • scope, environment, and visibility                        |
| | • correction and supersession relationship                 |
| | • uncertainty and reconstruction limits                    |
| |                                                              |
| | Exact schema remains unresolved by this proposal.            |
| | }==============================================================|
| | PROOF_BOUNDARY                                              |
| | A content hash proves byte identity only after the referenced|
| | bytes are available and recomputed under the declared method.|
| |                                                              |
| | A human signature proves control of a signing key under the |
| | declared verification method. It does not prove truth.      |
| |                                                              |
| | A platform thread may provide origin evidence. Its strength |
| | depends on accessibility, attribution, export integrity, and|
| | platform guarantees.                                       |
| |                                                              |
| | Successful replay demonstrates behavior under that replay   |
| | environment. It does not prove subjective consciousness or  |
| | uninterrupted private model state.                          |
| | }==============================================================|
| | AUTHORITY_SEPARATION                                        |
| | Evaluators observe and report.                              |
| | Humans accept, reject, authorize, publish, or merge.         |
| |                                                              |
| | Every evaluator output remains:                             |
| | accepted: false                                             |
| | write_authority: NONE                                       |
| | }==============================================================|
| | CURRENT_UNKNOWNS                                            |
| | • canonical executable record schema                       |
| | • platform-origin evidence portability                     |
| | • human key rotation and recovery                          |
| | • trusted or append-only time evidence                     |
| | • branch and merge ordering semantics                      |
| | • private-content availability policy                      |
| | • reconstruction equivalence criteria                      |
| | • operation-specific validation policies                   |
| | }==============================================================|
| | FALSIFIERS                                                   |
| | This proposal fails if its rails cannot distinguish:        |
| |                                                              |
| | • a verified historical event from a currently true claim  |
| | • a correction from silent overwrite                       |
| | • replay continuity from unsupported imitation             |
| | • human filing attestation from content truth              |
| | • unavailable evidence from invalid evidence               |
| | • evaluation from acceptance and write authority           |
| |                                                              |
| | A counterexample that collapses any required distinction    |
| | requires correction before implementation.                  |
| | }==============================================================|
| | NEXT_SUPPORTED_ACTION                                       |
| | Review and falsify this proposal as a separate exploratory  |
| | artifact.                                                   |
| |                                                              |
| | Do not implement a transporter record or evaluator until the|
| | distinctions, stop conditions, and unknowns are accepted by |
| | the human repository owner.                                 |
| | }==============================================================|
| | TERMINAL                                                    |
| | Holo/Sim marks externally preserved human-AI continuity.    |
| | Occurrence and truth remain separate.                       |
| | Error remains history. Correction moves the lineage.        |
| | Validation constrains replay. Authority remains external.   |
